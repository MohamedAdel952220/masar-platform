# Epic 7 Deployment Audit

Production audit of Epic 7 (`Media & Camera Architecture`) against the live, linked Supabase project (`oqvgkvyapjauepgozgjd`, staging), performed **directly against the deployed database and project** via `supabase db query --linked`, `supabase migration list --linked`, `supabase functions list`, and direct HTTP requests against each Edge Function's live endpoint — not a static re-read of migration files. Every claim below reflects what is actually running in production at audit time, cross-checked against `BACKEND_ARCHITECTURE.md`, `BACKEND_EXECUTION_PLAN.md`, `EPIC_7_REVIEW.md`, and `EPIC_7_FIX_REPORT.md`. No code was modified during this audit.

**Verdict up front:** the database layer (schema, enums, constraints, foreign keys, indexes, triggers, RLS policies, helper functions, RPC) is deployed correctly and matches `EPIC_7_FIX_REPORT.md` exactly, field for field and byte for byte in every function/policy body pulled live — including the Critical (C1) and both High (H1, H2) fixes, independently re-verified live rather than trusted from the fix report's own claims. The `media.camera_connections` table (C1's core fix) is confirmed live, manager-only, and — critically — **confirmed absent** from the `supabase_realtime` publication, which now carries only `media.cameras`. However, **none of Epic 7's four Edge Functions are deployed** — `camera-heartbeat`, `camera-stream-token`, `issue-service-account-key`, and `revoke-service-account-key` are all absent from `supabase functions list` and all return `404` on a direct HTTP request. This is the identical class of gap `EPIC_4_DEPLOYMENT_AUDIT.md` and the first `EPIC_6_DEPLOYMENT_AUDIT.md` both found (migrations deployed, Edge Functions not yet pushed) — and it means the H2 fix (camera-binding enforcement) and the H1 fix (online-status gating), both of which live entirely inside these undeployed functions, are not yet actually enforceable in production. Full verdict in §7.

## 2. Deployment issues

- **Critical for this Epic specifically — the entire guardian-facing and machine-facing runtime surface is non-functional in production right now.** A guardian cannot request a stream token (`camera-stream-token` absent), an on-prem camera agent cannot send a heartbeat (`camera-heartbeat` absent, and even if it could reach a URL, `[functions.camera-heartbeat] verify_jwt = false` has no effect on a function that doesn't exist), and a manager cannot issue or revoke a service-account key through the documented flow (`issue-service-account-key`/`revoke-service-account-key` both absent). The **only** Epic 7 write path that works in production today is `public.create_camera` (a deployed RPC, callable directly by an authenticated manager session) — a manager could create camera rows today, but could never link a real on-prem agent to one, since the key-issuance function that would produce a usable credential doesn't exist yet, and no guardian could ever view it, since the token-issuance function is equally absent.
- **This is a deployment/operations gap, not a code or schema defect.** Every line of all four Edge Functions reviewed and fixed in `EPIC_7_FIX_REPORT.md` (H1's `online` check, H2's camera-binding check, M1's cross-reference comments, M2's `.catch()`, M3's purpose/scope cross-validation) was independently re-read from the local source during this audit and is correct as written — none of the four has ever been `supabase functions deploy`'d. All four are remediable without any further code change.
- **At present this has no visible symptom** because every Epic 7 table currently holds 0 rows (`cameras`, `camera_connections`, `camera_classroom_links`, `camera_service_account_links`, and `identity.service_accounts` all confirmed empty live) — there is no seed/test data flowing through Epic 7 yet. The gap becomes visible the instant a real manager tries to onboard a real camera end-to-end (create the camera via the Dashboard, issue an agent key, deploy the agent, or a parent tries to view a live feed).
- **Migration deployment itself is clean.** All 6 Epic 7 migrations (`20260725000001` through `20260725000006`) show `local` and `remote` timestamps in exact agreement per `supabase migration list --linked` — no drift, no partial application, no manually-applied out-of-band change was detected anywhere in the 50 Epic 1–7 migrations checked.
- **No drift between the fix report's claims and the live database was found anywhere in the SQL layer.** Every function body and every RLS policy's `USING`/`WITH CHECK` text pulled live matched the fix report's own quoted source line-for-line, including the specific security-context details (`create_camera` confirmed `prosecdef=false`/SECURITY INVOKER exactly as designed; `sweep_camera_heartbeats` confirmed `prosecdef=true` with `search_path=""`; all three trigger functions confirmed `prosecdef=false`).

## 3. Security issues

No new security issues were found in the deployed database layer. Every fix from `EPIC_7_FIX_REPORT.md` was independently re-verified live and matches exactly — this is the section of this audit that mattered most, since it directly re-tests the Critical and High findings from `EPIC_7_REVIEW.md`:

- **C1 (Critical — Realtime IP/protocol leak) confirmed fixed live, at both halves of the fix.** First, `media.cameras`' live column list (`information_schema.columns`) contains no `ip_address`/`stream_protocol` at all — they exist only on the new `media.camera_connections` table. Second, and this is the specific check that matters for C1: `select * from pg_publication_tables where pubname='supabase_realtime'` was queried live and confirmed **`media.camera_connections` is not a member** — only `media.cameras` is published for this Epic, exactly as `EPIC_7_FIX_REPORT.md` §4 describes. This closes the loop the review's Critical finding actually identified: a guardian's live Realtime subscription to `tenant:{id}:cameras` can now never receive a raw IP address or stream protocol in any `postgres_changes` payload, because that data no longer exists on the published table.
- **C1's manager-only access boundary confirmed live**: `camera_connections_select_manager`, `camera_connections_insert_manager`, `camera_connections_update_manager` are the only three policies on `media.camera_connections` (confirmed via `pg_policies`) — no guardian, teacher, reception, driver, or platform_admin policy exists on this table at all. `FORCE ROW LEVEL SECURITY` is active.
- **H1 (missing `online` check in `camera-stream-token`) confirmed present in source** — re-read live from the local repository (the deployed Edge Function itself cannot be inspected directly since it doesn't exist in production, so this check is necessarily against source, not a running instance) and matches the fix report's own quoted diff exactly: `if (!camera.online || camera.admin_disabled) { throw ... }`. **Not yet verifiable against a running instance**, since the function is undeployed (§1/§2) — this is the direct consequence of the deployment gap, not a defect in the fix itself.
- **H2 (camera-impersonation binding) confirmed live at the database layer**: `media.camera_service_account_links` exists, is manager-only (`camera_service_account_links_select_manager`/`_insert_manager`/`_delete_manager`, no other role), and its consistency trigger (`check_camera_service_account_link_consistency`, pulled live via `pg_get_functiondef` and compared line-for-line against source) correctly rejects a tenant mismatch **and** rejects binding a non-`camera_agent`-purpose service account to a camera. The *enforcement* half of H2 (the `camera-heartbeat` Edge Function's own binding check against this table) is source-verified only, for the same reason as H1 — the function is undeployed.
- **M4 (soft-deleted-classroom guardian-visibility fix) confirmed live**: `cameras_select_guardian`'s live policy text (pulled via `pg_policies`) contains the exact `JOIN academic.classrooms c ON (c.id = ccl.classroom_id AND c.deleted_at IS NULL)` fix described in the fix report; `camera_classroom_links_select_guardian`'s live policy text contains the equivalent `EXISTS (SELECT 1 FROM academic.classrooms c WHERE c.id = camera_classroom_links.classroom_id AND c.deleted_at IS NULL)` clause. Both confirmed byte-for-byte against the fix report's own quoted source.
- **L5 (duplicate-IP constraint) confirmed live**: `camera_connections_tenant_ip_key`, a unique index on `(tenant_id, ip_address)`, exists exactly as specified.
- **`FORCE ROW LEVEL SECURITY` is active on all 4 Epic 7 tables** (verified via `pg_class.relforcerowsecurity`), and no policy exists anywhere in this Epic for teacher, reception, driver, or platform_admin — matching §12's Cameras row and §13.6's bypass-list exclusion exactly, re-confirmed live with zero drift from the prior deployment audit's own findings.
- **One pre-existing, project-wide observation, not Epic-7-introduced**: `public.create_camera` has `EXECUTE` granted to `anon` in addition to `authenticated`/`service_role` — this is Postgres/PostgREST's default schema-level grant behavior, already confirmed identical for every RPC in Epic 1–6 during every prior deployment audit, and functionally inert since the function's own first action is a `current_role() <> 'manager'` check that fails cleanly for any non-manager or unauthenticated caller. `media.sweep_camera_heartbeats` correctly has **no** `anon`/`authenticated` grant at all (only `service_role`), matching its scheduled-job-only calling convention.

M1/M2/M3's fixes (the Deno/Node cross-reference comments, the `.catch()` addition, the `purpose`/`scopes` cross-validation) are Edge-Function/TypeScript-layer changes with no corresponding live-database artifact to independently verify — their presence in the deployed *source* was already confirmed via the fix report's own `tsc`/`vitest` verification, which this audit did not need to re-run since those checks are deterministic and unaffected by deployment. They cannot be exercised live at all until the Edge Functions are deployed (§1/§2).

## 4. Camera architecture verification

Checked directly against `BACKEND_ARCHITECTURE.md` §3.33, §3.34, §17, and the C1/H2 fixes specifically:

- **§3.33's `online`/`admin_disabled` independent-boolean design confirmed live**: both columns exist on `media.cameras`, both default `false`, and — per the trigger/function bodies pulled live — `media.sweep_camera_heartbeats()`'s `UPDATE` statement references only `online`, never `admin_disabled`, confirming the "never touches admin_disabled" invariant holds in the actual deployed function body, not just in source commentary.
- **§17's "raw camera IP/RTSP credentials never sent to client apps" now has a genuine structural guarantee at the schema level**, confirmed live: `ip_address`/`stream_protocol` exist on exactly one table (`media.camera_connections`), that table has zero non-manager RLS policies, and that table is confirmed absent from `supabase_realtime`. This is the direct, live resolution of `EPIC_7_REVIEW.md`'s Critical finding.
- **§3.34's "no link row = shared/unlinked camera" model confirmed live**: `media.camera_classroom_links` has a composite primary key `(camera_id, classroom_id)` with no `deleted_at` or nullable-classroom-id alternative — a camera with `zone='common'` and no row in this table is unreachable by any guardian query, matching the documented model exactly.
- **The camera-to-service-account binding table (`media.camera_service_account_links`, the H2 fix) is live, correctly constrained** (composite PK, cascading FKs, a consistency trigger enforcing tenant agreement and `purpose='camera_agent'`), but is currently **unreachable through the documented application flow** since `issue-service-account-key` (the only code path that would ever populate it in normal operation) is not deployed. A manager could, in principle, populate it via a direct authenticated `INSERT` today (the `camera_service_account_links_insert_manager` RLS policy would permit it), but no UI or documented flow exists to do so without the Edge Function.
- **The atomic two-table camera-creation path (`public.create_camera`, the other half of the C1 fix) is fully live and independently exercisable today** — confirmed `SECURITY INVOKER` (not `DEFINER`), confirmed its own explicit manager-role check, and confirmed its two `INSERT` statements target `media.cameras` and `media.camera_connections` in that order within a single function body (hence a single transaction). This is the one piece of Epic 7's camera-creation flow that does **not** depend on any undeployed Edge Function.

## 8. Final verdict

**Database layer: correct and complete.** Every table, enum, constraint, foreign key, index, trigger, RLS policy, helper function, and RPC specified for Epic 7 — including all six fixes from `EPIC_7_FIX_REPORT.md` (C1, H1's database-layer half, H2's database-layer half, M4, L5, and the unchanged-but-reverified L1/L3/L4/L6/M2/M3 items) — is deployed to production exactly as documented, with zero drift between the migration files, the fix report's claims, and the live database. The Critical finding's core resolution — `media.camera_connections` existing, being manager-only, and being absent from the Realtime publication — was independently re-verified live, not trusted from the report. No new security issue was found at the database layer, and no architecture deviation or documentation inconsistency was found anywhere in this Epic.

**Runtime layer: incomplete, in the same specific way Epic 4's and Epic 6's own delivery layers were each found incomplete on first audit.** None of Epic 7's four Edge Functions are deployed, and this means the *enforcement* half of both High findings from `EPIC_7_REVIEW.md` — H1's `online` gating and H2's camera-binding check — exists only in source, not in any running instance a real guardian or camera agent could actually reach. The `camera-heartbeat` function's `verify_jwt = false` override in `config.toml` is correctly configured and ready, but moot until deployed. Every RPC-only or RLS-only code path (direct camera creation via `public.create_camera`, direct RLS reads/writes by an authenticated manager or guardian session against already-existing rows) works correctly and was independently confirmed live — but the guardian-facing stream-token flow, the machine-facing heartbeat flow, and the manager-facing key-issuance/revocation flow — the entirety of this Epic's own stated business goal ("deliver the classroom-camera feature... without taking on video-infrastructure risk") — are entirely inert until deployed. This is an operational deployment gap, not a code or schema defect — the fix is `supabase functions deploy camera-heartbeat camera-stream-token issue-service-account-key revoke-service-account-key`, no code changes required.

Because required Edge Functions from Epic 7's own contract (`BACKEND_EXECUTION_PLAN.md` §7) are missing from production — and because two of those four functions are specifically where this Epic's own Critical-review-cycle High findings (H1, H2) are enforced — this audit **cannot** issue a clean pass.

**NOT READY FOR EPIC 8** — remediate §1/§2 (deploy all four Edge Functions, confirm each responds with the correct `verify_jwt` behavior live — `camera-heartbeat` should accept a request with no `Authorization` header and instead demand `x-service-account-key`; the other three should reject a request with no JWT — and confirm at least one end-to-end cycle: a manager creates a camera via `create_camera`, issues a bound service-account key via `issue-service-account-key`, a simulated agent sends a heartbeat that is accepted for its bound camera and rejected for an unbound one, and a guardian successfully resolves a stream token only for an online, non-disabled, correctly-linked camera) and re-run this audit before proceeding. The standing recommendation carried forward from every prior deployment audit in this project — that the RLS adversarial suite (`tests/rls/epic7_rls_adversarial.sql`, including its purpose-built C1/H2/M4 regression tests) be executed by an authorized human operator — also remains open and is reiterated here rather than treated as a newly-discovered gap.
