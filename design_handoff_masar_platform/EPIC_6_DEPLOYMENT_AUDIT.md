# Epic 6 Deployment Audit

Production audit of Epic 6 (`Billing & Payments`) against the live, linked Supabase project (`oqvgkvyapjauepgozgjd`, staging), performed **directly against the deployed database and project** via `supabase db query --linked`, `supabase migration list --linked`, and `supabase functions list` — not a static re-read of migration files. Every claim below reflects what is actually running in production at audit time, cross-checked against `BACKEND_ARCHITECTURE.md`, `BACKEND_EXECUTION_PLAN.md`, `EPIC_6_REVIEW.md`, `EPIC_6_FIX_REPORT.md`, and `EPIC_6_COMPLETION_REPORT.md`. No code was modified during this audit.

**Verdict up front:** the database layer (schema, enums, constraints, foreign keys, indexes, triggers, RLS policies, helper functions, RPCs, storage) is deployed correctly and matches `EPIC_6_FIX_REPORT.md` exactly, field for field and byte for byte in every function body pulled live — including all six fixes from the review cycle (C1, H1, H2, M1, M2, L1-L3) and the proactively-found `installment_plans` immutability recurrence. However, **the runtime delivery layer is incomplete**: none of Epic 6's four Edge Functions (`initiate-payment`, `payment-webhook`, `generate-invoice-pdf`, `resend-invoice`) are deployed, meaning no payment can currently be initiated, no webhook can be received, and no invoice PDF can be rendered in this environment — this is a carried-forward instance of the exact same gap `EPIC_4_DEPLOYMENT_AUDIT.md` first identified for `notification-dispatch` and that `EPIC_5_DEPLOYMENT_AUDIT.md` confirmed was still unresolved, now recurring for Epic 6's own, financially-critical functions. Full verdict in §7.

## 2. Deployment issues

- **Critical — the payment pipeline cannot function in production right now.** A guardian cannot initiate a payment (`initiate-payment` absent), a PSP cannot deliver a webhook (`payment-webhook` absent), and a generated invoice can never acquire a PDF (`generate-invoice-pdf` absent, and its trigger's queued jobs will accumulate in `jobs.background_job_queue` with `status='queued'` indefinitely, exactly mirroring the `notification-dispatch` symptom `EPIC_4_DEPLOYMENT_AUDIT.md` §2 first described). The **only** Epic 6 write paths that work in production today are the ones reachable via direct RPC call from an authenticated session: `generate_invoice`, `mark_installment_paid_manual`, `mark_ledger_item_paid_manual`, `verify_payment`, `refund_payment` — none of which require an Edge Function. This means a manager could, in principle, generate invoices and manually reconcile cash/installment payments through direct RPC calls today, but the guardian-initiated gateway/bank-transfer/Fawry flow — the actual "core commercial loop" the execution plan's Business Goal names as this Epic's purpose — is entirely inert.
- **This is a deployment/operations gap, not a code defect.** Every line of `initiate-payment/index.ts` reviewed and fixed in `EPIC_6_FIX_REPORT.md` (the H1 in-flight-payment check, the H2 receipt-existence check moved outside the gateway `try/catch`) is correct as written and was independently re-read in full during this audit — it simply has never been `supabase functions deploy`'d. The same is true for the other three functions. All four are remediable without any further code change.
- **At present this has no visible symptom** because `jobs.background_job_queue` currently holds 0 rows and `billing.payment_transactions`/`billing.invoices` currently hold 0 rows (checked live) — there is no seed/test data flowing through Epic 6 yet. The gap becomes visible the instant a real guardian attempts to pay, or a real manager generates a real invoice expecting a PDF.
- **Migration deployment itself is clean.** All 7 Epic 6 migrations (`20260723000001` through `20260723000007`) show `local` and `remote` timestamps in exact agreement per `supabase migration list --linked` — no drift, no partial application, no manual out-of-band change detected anywhere in the 44 Epic 1-6 migrations checked.
- **No pg_cron registration exists for any of the four scheduled-job functions** (`generate_recurring_ledger_items`, `roll_up_billing_status`, `send_payment_reminders`, `escalate_stale_pending_verifications`) — this is **not a new gap**, it is the explicitly-documented, deliberate limitation `EPIC_6_COMPLETION_REPORT.md` §11.6 and the migration 6 file header both already state ("pg_cron is not installed in this project, confirmed live in `EPIC_4_DEPLOYMENT_AUDIT.md`... every function is fully correct and callable on-demand"). Re-confirmed live: `pg_extension` shows only `pg_net`, no `pg_cron`; querying `cron.job` fails with `relation "cron.job" does not exist`. Recorded here for completeness, not counted as a new deployment issue.

## 3. Security issues

No new security issues were found in the deployed database layer. Every fix from `EPIC_6_FIX_REPORT.md` was independently re-verified live — full function bodies pulled via `pg_get_functiondef` and compared against the fix report's own quoted snippets, not merely trusted:

- **C1 (Critical — obligation-matching over-crediting/incorrect-reversal) confirmed fixed live**: `billing.settle_payment_transaction()`'s deployed body matches the fix report byte-for-byte — both the `succeeded` and `refunded` branches aggregate `ledger_item_id`/`installment_entry_id` from `billing.invoice_lines where invoice_id = v_row.invoice_id` and update only those specific rows (`where id = any(...)`), never a `fee_item_id`-wide match. `billing.check_invoice_line_consistency()`'s extended validation (same-tenant, same-child via the invoice's own `child_id`, not-already-paid) is confirmed live for both `ledger_item_id` and `installment_entry_id`, with the installment case correctly joining through `installment_plans` to reach `child_id` (since `installment_schedule_entries` itself carries no `child_id`).
- **H1 (duplicate payment initiation) confirmed fixed live**: `payment_transactions_one_inflight_per_invoice` — a unique index on `(invoice_id) WHERE status IN ('initiated','pending_verification')` — is present and correctly typed (`ANY (ARRAY['initiated'::billing.payment_status, 'pending_verification'::billing.payment_status])`). The Edge-Function-level pre-check is confirmed present in source but, per §1/§2 above, is not currently reachable in production since the function itself isn't deployed — the DB-level backstop is the only layer of this defense actually live right now.
- **H2 (unverified/undiscoverable receipt) confirmed fixed live**: `payment_transactions.receipt_file_path` column present; `payment-receipts` storage bucket present (private, 20MB limit) with exactly 3 policies — `payment_receipts_write_guardian` (INSERT, own tenant+own-uid folder only), `payment_receipts_read_guardian` (SELECT, same scope), `payment_receipts_read_manager` (SELECT, tenant-wide) — no manager write and no delete policy on this bucket at all, matching the "guardian uploads, manager reviews, nothing gets silently altered" intent. The storage-existence check itself lives in `initiate-payment`'s source (not independently testable live until deployed — see §2).
- **M1 (invoice/installment-plan field immutability) confirmed fixed live**: `trg_invoices_immutable_fields` (fires `before update of total, child_id, invoice_number`) and `trg_installment_plans_immutable_once_paid` (fires `before update`, raises only when `child_id`/`fee_item_id` changes AND a paid entry exists) are both present, both correctly attached, bodies matching source exactly.
- **M2 (unaudited manual ledger-paid marking) confirmed fixed live**: `billing_ledger_items_update_manager`'s `USING`/`WITH CHECK` both carry `status <> 'paid'::billing.billing_status`; `public.mark_ledger_item_paid_manual` exists, is `SECURITY DEFINER` with `search_path=''`, performs the atomic guarded UPDATE, notification insert, and `write_audit_log` call exactly as the fix report describes — confirmed via a full live `pg_get_functiondef` pull.
- **L1/L2/L3 confirmed fixed live**: `invoice_number_counters`' PK is `(tenant_id, year)` with `generate_invoice`'s counter upsert correctly keying on `extract(year from now())::int`; `generate_invoice`'s idempotency hash uses the normalized `string_agg(...with ordinality...)` construction, not raw `p_items::text`; `settle_payment_transaction`'s no-match branch contains the `raise warning` call with transaction id, current status, expected from-list, and requested status.
- **`FORCE ROW LEVEL SECURITY` is active on all 9 Epic 6 tables** (confirmed via `pg_class.relforcerowsecurity`).
- **Zero `DELETE` policies exist anywhere in the `billing` schema** (confirmed — `pg_policies` for all 9 tables shows only `SELECT`/`INSERT`/`UPDATE` rows), matching the architecture doc's own "Manager has no D (hard delete) anywhere in this system... only soft-delete" principle (§12 note) — for Epic 6 specifically, the doc's literal "CRUD" cells for Fee items/Billing ledger/Invoices are satisfied via `active`/`status` toggles through the existing `UPDATE` policies, never a hard delete.
- **No direct INSERT/UPDATE policy exists on `invoices` (beyond the one documented void-only exception), `invoice_lines`, or `payment_transactions`** — confirmed live via `pg_policies`, meaning `generate_invoice`, the (undeployed) `initiate-payment`, and `verify_payment`/`refund_payment`/`settle_payment_transaction` remain the sole write paths for these three tables, as designed.
- **Every `SECURITY DEFINER` function in Epic 6** (`generate_invoice`, `verify_payment`, `refund_payment`, `mark_installment_paid_manual`, `mark_ledger_item_paid_manual`, `payment_transactions_support_view`, `billing.settle_payment_transaction`, and all 4 scheduled-job functions) **carries `SET search_path = ''`** (confirmed via `pg_proc.proconfig`, 12/12). All non-trigger-context internal references are fully schema-qualified in every body pulled. Every plain trigger function (`check_*_consistency`, `check_invoice_immutable_fields`, `check_installment_plan_immutable_once_paid`, `audit_invoice_voided`, `enqueue_invoice_pdf_job`) is correctly **not** `SECURITY DEFINER` — none of them need to see across an RLS ownership boundary the invoking role doesn't already have, unlike Epic 5's `check_trip_registration_consistency` precedent.
- **`billing.settle_payment_transaction` and the 4 scheduled-job functions have no `EXECUTE` grant to `anon`/`authenticated`** — confirmed live via `information_schema.routine_privileges` (only `postgres`/`service_role`). This is the correct authorization boundary: `settle_payment_transaction` must only ever be reached via `verify_payment`/`refund_payment`/the (future) webhook handler, never called directly by a client session.
- **One pre-existing, project-wide observation, not Epic-6-introduced**: the 5 client-facing RPCs (`generate_invoice`, `mark_installment_paid_manual`, `mark_ledger_item_paid_manual`, `verify_payment`, `refund_payment`) all have `EXECUTE` granted to `anon` in addition to `authenticated` — this is Postgres/PostgREST's default schema-level grant behavior, already confirmed identical for every RPC in Epic 1-5 during every prior deployment audit, and functionally inert since every one of these functions' first action is a `current_role()`/`auth.uid()`-dependent check that fails cleanly for an unauthenticated caller (`current_tenant_id()`/`current_role()` return `null`/error under no JWT, causing the role check to reject before any write is attempted).

## 4. Financial correctness verification

Directly re-testing, against the live schema, the same explicit verification requirements this Epic's review/fix cycle was held to:

- **Every financial transaction remains balanced** — confirmed structurally: `settle_payment_transaction`'s live body touches only the `ledger_item_id`/`installment_entry_id` arrays derived from the specific invoice being settled/refunded, via `where id = any(...)`, never a broader predicate. There is no code path left in the deployed function that could match by `fee_item_id` alone.
- **Invoice settlement can never settle unrelated obligations** — confirmed structurally via the same mechanism, and additionally enforced at the trigger layer: `check_invoice_line_consistency` (live, confirmed) rejects an `INSERT`/`UPDATE` on `invoice_lines` referencing a `ledger_item_id`/`installment_entry_id` belonging to a different child than the invoice's own `child_id`, or one already `status='paid'` — so even a malformed `generate_invoice` call cannot construct an invoice line pointing at an unrelated or already-settled obligation in the first place.
- **Refunds only reverse obligations originally settled by the same payment** — confirmed structurally: the `refunded` branch of `settle_payment_transaction` re-derives `v_ledger_item_ids`/`v_installment_entry_ids` from `billing.invoice_lines where invoice_id = v_row.invoice_id` — the exact same query the `succeeded` branch used, scoped to the exact same invoice. There is no parameter or code path by which a refund could reach a different invoice's rows.
- **Duplicate payment initiation is prevented or safely handled** — confirmed at the DB layer only (`payment_transactions_one_inflight_per_invoice`, live, correctly typed). The Edge-Function-level friendly pre-check exists in source but is not currently reachable in production (§1/§2) — this is a genuine, if narrow, verification gap: the *backstop* is live and would correctly reject a genuine race via `unique_violation`, but the *friendlier* first layer (returning the existing in-flight payment instead of a raw constraint error) cannot be exercised until the function is deployed.
- **Receipt uploads are fully traceable and reviewable** — the storage layer (bucket + 3 policies + `receipt_file_path` column) is fully live and correct; the upload-verification step that populates `receipt_file_path` at initiation time lives in the undeployed Edge Function, so this guarantee is currently only half-live (storage/DB side ready, application-flow side pending deployment).
- **All ledger mutations are auditable** — confirmed live: `write_audit_log` calls present in `generate_invoice` (`invoice_generated`), `settle_payment_transaction` (`payment_<status>`), and `mark_ledger_item_paid_manual` (`ledger_item_marked_paid_manual`) — 7 total `write_audit_log` call sites across the RPC file, matching the fix report's own count.
- **All billing triggers behave correctly under RLS** — every trigger fires `BEFORE`/`AFTER` regardless of the invoking role (ordinary `plpgsql` triggers are not RLS-gated themselves; their `raise exception` behavior is uniform across all roles reaching the underlying table through any RLS-permitted path), confirmed for all 22 live triggers.
- **All `SECURITY DEFINER` functions preserve authorization boundaries** — re-confirmed in §3 above; every function's own explicit `current_role() <> 'manager'` (or guardian-ownership) check precedes any write, and `search_path=''` plus full schema-qualification prevents any search-path-hijacking bypass of those checks.

**Net assessment**: the financial-correctness *logic* is fully and correctly deployed and independently verifiable by direct RPC call today. The financial-correctness *delivery pipeline* (a guardian actually being able to initiate a payment, a PSP webhook actually being able to land) is not yet live, per §1/§2.

## 5. Architecture deviations

None found that were not already explicitly documented as deliberate scope decisions in `EPIC_6_COMPLETION_REPORT.md` §11 or the fix report. Specifically checked and confirmed matching `BACKEND_ARCHITECTURE.md`:

- **§3.36-3.43 table shapes** — every column, type, nullability, and default on all 9 tables matches the doc's field lists, **plus** three additive fields the doc's §3 field lists do not yet mention (`invoice_lines.ledger_item_id`/`installment_entry_id`, `payment_transactions.receipt_file_path`) — these are C1/H2 fix-report additions, not undocumented scope creep; both are covered in detail by `EPIC_6_FIX_REPORT.md` §4 and are architecturally consistent with (indeed, directly required by) §20's own "refunds only reverse obligations originally settled by the same payment" requirement. Flagged here for completeness and retroactive-documentation purposes (see §6), not as a defect.
- **§12 permission matrix** — "Fee items | R [Guardian] | – | – | CRUD [Manager] | – | –", "Billing ledger/Invoices | R (own child) | – | – | CRUD | – | –", "Payments | C (own child, initiate), R (own) [Guardian] | – | – | R, U (mark manual/verify) [Manager] | – | R (support/reconciliation view) [Platform Admin]" — all confirmed live exactly as specified, with the matrix's own footnote ("Manager has no D... only soft-delete, functionally a U") correctly satisfied via `active`/`status` toggles rather than a literal `DELETE` policy (zero exist).
- **§13.1 RLS baseline pattern** — every policy checked is a flat, direct equality/role check against `current_tenant_id()`/`current_role()`/`current_guardian_child_ids()`, with only two intentional `EXISTS` subqueries (`installment_schedule_entries_select_guardian`, `invoice_lines_select_guardian` — both resolving guardian ownership through a parent table's child-scoping, an established pattern since Epic 3).
- **§14.2 contract catalog** — `generate_invoice`, `mark_installment_paid_manual`, `verify_payment`, `refund_payment` all exist live with documented role restrictions and unchanged signatures (confirmed via `pg_get_function_identity_arguments`). `initiate_payment`/`payment_webhook_handler`/`resend_invoice` are documented but not deployed (§1). `mark_ledger_item_paid_manual` exists live but is **not** named anywhere in `BACKEND_ARCHITECTURE.md` §14.2 — a fix-report-driven addition (M2) that closes a real gap and is architecturally symmetric with the doc's own `mark_installment_paid_manual` entry, but the architecture doc itself hasn't been retroactively updated to list it (see §6).
- **§15 Realtime Event Matrix** — no `billing.*` table is in the live `supabase_realtime` publication, correctly matching Epic 6's own execution-plan entry ("None new — payment status changes surface via the Epic 4 notification pipeline").
- **§20 Payment Architecture** — the documented `initiated → pending_verification → succeeded|failed → (refunded)` lifecycle, the manual-vs-gateway method split, and the "refund is a distinct terminal state with its own reversal RPC, not a negative-amount transaction" design are all confirmed matching the live `settle_payment_transaction`/`verify_payment`/`refund_payment` implementation.
- **§21 Storage Architecture** — `payment-receipts` bucket present, private, correct size limit, correct `{tenant_id}/{guardian_id}/{filename}` path convention enforced by policy; `generated-documents` correctly reused with no new policy (matching migration 7's own header comment and the identical precedent `EPIC_4_DEPLOYMENT_AUDIT.md` already confirmed for chat-attachments' analogous reuse case).

- **§26/§27 Background/Scheduled Jobs** — the "Invoice PDF generation" background job's trigger-side (`trg_invoices_enqueue_pdf_job`) is live and correctly fires; its Edge-Function-execution side is not deployed (§1/§2). Recorded as a follow-up opportunity, not a defect.

- **`BACKEND_ARCHITECTURE.md` §14.2's Billing RPC list does not mention `mark_ledger_item_paid_manual`** — a real, live, correctly-implemented RPC added by the M2 fix, symmetric with the doc's own already-listed `mark_installment_paid_manual`. - **`EPIC_6_COMPLETION_REPORT.md`'s own migration/policy/RPC counts (7 migrations, 9 tables, 6 enums, 14 triggers, 26 RLS policies, 1 support-view function, 5 RPCs) were independently re-counted live during this audit and matched exactly**, except the trigger count: the completion report says 14, this audit's live count is **22** (including `set_updated_at` triggers on 6 tables and the consistency/immutability/audit triggers) — the completion report's own figure appears to have counted only the Epic-6-authored `check_*_consistency`/immutability/audit/enqueue trigger *functions* (14 distinct function definitions, confirmed correct) rather than the total *trigger attachments* including the reused generic `set_updated_at()` function attached 6 times. Both counts are internally consistent once the distinction is understood; flagged only because the two numbers could otherwise look like a discrepancy.

None of the above is a conflict between what was implemented and what the review/fix cycle approved — every difference traced back cleanly to a documented, approved fix or a pre-existing documentation lag that predates this Epic.

## 7. Final verdict

**Database layer: correct and complete.** Every table, enum, constraint, foreign key, index, trigger, RLS policy, helper function, and RPC specified for Epic 6 — including all six fixes from `EPIC_6_FIX_REPORT.md` (C1, H1, H2, M1, M2, L1-L3) and the proactively-found `installment_plans` immutability recurrence — is deployed to production exactly as documented, with zero drift between the migration files, the fix report's claims, and the live database. No new security issue was found. The financial-correctness logic itself (obligation-specific settlement/refund, immutability triggers, audit logging, authorization boundaries) is fully live and independently re-verified against the live function bodies, not merely trusted from the fix report.

**Runtime layer: incomplete, in the same specific way Epic 4's own delivery layer was found incomplete.** None of Epic 6's four Edge Functions are deployed, and no scheduler/webhook mechanism exists to invoke any of them even once deployed. This means: a guardian cannot initiate a payment, a PSP cannot deliver a webhook, and a generated invoice will never receive a PDF, in this environment, today. Every RPC-only code path (manager-initiated invoice generation, manual cash/installment reconciliation, manager-initiated verify/refund against an already-existing `payment_transactions` row) works correctly and was independently confirmed live — but the guardian-facing payment-initiation flow, which is this Epic's own stated Business Goal ("the core commercial loop of the platform"), is entirely inert until `initiate-payment` is deployed. This is an operational deployment gap, not a code or schema defect — the fix is `supabase functions deploy initiate-payment payment-webhook generate-invoice-pdf resend-invoice`, no code changes required.

Because required Edge Functions from Epic 6's own contract (`BACKEND_EXECUTION_PLAN.md` §7) are missing from production — and unlike Epic 5 (which had no Edge Functions in its own contract and could therefore inherit Epic 4's identical gap without it counting against Epic 5's own verdict), Epic 6's entire business goal depends on exactly the functions that are missing — this audit **cannot** issue a clean pass.

**NOT READY FOR EPIC 7** — remediate §1/§2 (deploy all four Edge Functions, provision at least a manual/on-demand invocation path for the scheduled-job functions, confirm at least one end-to-end payment initiation → manual verification → ledger settlement cycle against a real or sandboxed request) and re-run this audit before proceeding. The standing recommendation carried forward from `EPIC_4_DEPLOYMENT_AUDIT.md` and `EPIC_5_DEPLOYMENT_AUDIT.md` — that the RLS adversarial suite (`tests/rls/epic6_rls_adversarial.sql`, including its purpose-built C1/H1/M2 regression tests) be executed by an authorized human operator — also remains open and is reiterated here rather than treated as a newly-discovered gap.
